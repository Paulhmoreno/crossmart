# Implementation plan

## Scope and ownership

Self-hosted Crossmart, preserving the upstream backend and web architecture. Odoo 18 is authoritative for product identity, SKU, barcode, variants, base price, available stock and original product photographs/documents. Crossmart owns commercial content, channel-specific adaptations, listings and operational status. Existing Crossmart media facilities handle copies for publication; no separate media manager.

Odoo integration must use its supported API with a least-privilege read-only account. Read the product Documents relation and its authorized attachments; classify publication images separately from manuals and other internal files. Verify actual models, permissions and media retrieval before designing the integration. Keep private source files private. Preserve commercial edits during sync and prevent duplicate products, duplicate inventory changes and unintended Odoo writes.

### Phase 1 verified status (`feat/odoo`)

- **Connection and security**: Single-screen Spanish (Ecuador) configuration under Settings (`Odoo ERP`) with connection test, encrypted credential storage via native `EnvelopeEncryption`, optional collapsible advanced mapping (warehouse, pricelist, stock field, brand field, custom fields, sync interval), read-only preview search, selective sync, full-catalog sync behind explicit confirmation, and non-destructive disconnect. The Odoo client strictly allowlists read-only JSON-RPC methods (`fields_get`, `search`, `search_read`, `search_count`, `read`).
- **Live read-only verification**: Validated against a live Odoo 18 instance (read-only) with three representative real products (standard barcoded item with main photo + `product.document` gallery images, generic item without barcode, and zero-stock barcoded item with gallery attachments). Verified initial sync, new document photo incorporation on repeat sync, zero duplicate products/media/stock movements, commercial edit preservation, native media serving, and unrestricted manual product CRUD.
- **Closure hardening**: Distinguished empty document queries from transient document read failures (preserving previously synced photos and private documents and reporting sync issues instead of clean completion), blocked changing Odoo URL/database once Odoo products exist (plus per-connection and origin guards), restricted commercial gallery promotion strictly to non-sensitive `product.document` raster images (keeping loose chatter attachments and sensitive/technical images private), and extended document queries to variant-level `product.product` records.
- **Source ownership enforcement**: Enforced per product/variant (`sourceKind = ODOO`) across single-product updates, variant price updates, bulk actions, CSV imports, manual stock adjustments, mark-sold, and product deletion, with read-only UI indicators (`Origen: Odoo` and `"Este dato se administra desde Odoo"`).
- **Observed live limits**: The live Odoo 18 catalog contained zero multi-variant templates, zero variant-level document rows, and zero non-image technical PDFs at verification time; multi-variant sync, variant-level document ingestion, and private non-image document classification/download are implemented and covered by unit tests, awaiting live source records when added to the ERP.

### Phase 2 verified status (`feat/woocommerce`)

- **Full Odoo catalog synchronization**: Executed an authorized full-catalog read-only sync against the live Odoo 18 source. All active eligible products synchronized with zero failures, zero duplicates, preserved commercial edits, native local media storage, and zero automatic channel publications.
- **Native WooCommerce channel connector**: Implemented directly on Crossmart's channel SDK (`SellerCredentialsConnector`, `CatalogSource`, `ListingPublisher`, `TaxonomyProvider`, `InventorySync`) without a parallel publishing engine or separate media manager. Credentials are stored via native envelope encryption, sent exclusively over HTTPS using HTTP Basic Auth headers (never query-string secrets), and tested via a non-mutating `POST .../channel-connections/credentials/test` endpoint.
- **Deduplication and remote identity**: Existing remote catalog imports link strictly by existing remote listing ID or exact SKU match (handle/name-only matching is disabled for WooCommerce). Publishing verifies remote SKU conflicts before creating new products, stores persistent remote product/variation IDs per store, and reads back persisted remote products and images after write.
- **Remote photography transfer**: Solves local-to-remote photo delivery without public tunnels or exposing localhost: reuses persisted remote WordPress Media IDs (`_crossmart_media_map`), reads local Crossmart files directly from `FileStorage` (`readByUrl`) and uploads binary payloads to `/wp-json/wp/v2/media` when an authorized WordPress Application Password (`upload_files`) is configured, allows direct sideloading for already-public HTTPS image URLs, and explicitly fails with a missing-images requirement when local images cannot be uploaded to the remote store.
- **Orders and webhooks safety**: Implemented read-only `WooCommerceOrderSource` and signed HMAC-SHA256 webhook verification (`verifyWooCommerceWebhook`) with unit coverage, while keeping `FetchOrders` and `ReceiveWebhooks` disabled in connector capabilities during Phase 2 so automatic order ingestion and stock deductions cannot run before reconciliation is proven.
- **Single-screen Spanish (Ecuador) UI**: Promoted WooCommerce to a live native store in Crossmart Web with a single-screen Spanish connection dialog (`URL de la tienda (HTTPS)`, `Consumer Key`, `Consumer Secret`, collapsible WordPress Media & default status options), live `Probar conexión` verification, credential update action on connected stores, and store details showing store URL, currency/tax mode, remote product count, default status, and WordPress media readiness.
- **Live WooCommerce and WordPress Media validation**: Verified against an authorized WooCommerce store using encrypted credentials (`defaultStatus = draft`): remote catalog read, categories (including HTML-entity decoding) and global attributes read, cross-check of remote SKUs against all Odoo-imported products without modifying existing products, explicit failure without remote creation when local images lack WordPress Media auth, binary upload of a multi-photo Odoo product's main and gallery images to WordPress Media (all remote image URLs verified HTTP 200), draft product creation and read-back verification (title, HTML description, short description, SKU, EAN/`global_unique_id`, category, price, inventory, `draft` status, persistent remote ID and media map), and repeat updates confirming zero duplicate products and exact reuse of previously uploaded WordPress Media IDs. Automatic order ingestion and live webhooks remain disabled.

## Later phases: design constraints

WooCommerce: retain upstream connector SDK and simple credential-based setup; consult the prior working implementation and official REST API as references. Reuse only rights-cleared code where it fits natively. Check persisted and visible results, including images and taxonomy.

Mercado Libre: extend the existing native connector rather than replacing it. Compare official [API validation](https://developers.mercadolibre.com.ec/validaciones), [category/attribute rules](https://developers.mercadolibre.com.ec/categorias-y-atributos), [notifications](https://developers.mercadolibre.com.ec/productos-recibe-notificaciones) and [moderations](https://developers.mercadolibre.com.ec/gestionar-moderaciones) with the native connector and community references [fedeclavero/mercadolibre-mcp](https://github.com/fedeclavero/mercadolibre-mcp), [dedero1985/mercadolibre-mcp](https://github.com/dedero1985/mercadolibre-mcp) and [matuck40/mercadolivre-mcp](https://github.com/matuck40/mercadolivre-mcp). Treat these as references, not dependencies or proof of Ecuador support. Verify MEC behavior and live authorization; use official rules for allowed corrections, do not automatically relist prohibited items.

Customer-facing sales agent: separate future evaluation, not part of this mission. Crossmart's native operator agent and catalog API/MCP may serve as product knowledge; do not rebuild a customer inbox or expose internal agent permissions to buyers. Evaluate a self-hosted inbox such as Chatwoot and channel-specific messaging APIs separately. Mercado Libre questions and post-sale messaging must respect channel rules. No implementation until explicitly scoped.

## Completion policy

The next phase begins after the current functional result is checked. Keep the original documentation and conventions. No additional channels or dropshipping. Prefer observed outcomes over test counts. Only publish generic, non-sensitive evidence in public repositories; keep environment details and business data in private local records.
